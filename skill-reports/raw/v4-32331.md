The branch `pr-32331` (3 commits, up to date with `origin/main`) changes mathtext so that relation, binary and arrow operators get no 0.2 em space on a side that touches the start or end of the expression, a `{...}` group or a delimiter (gh-23315). It also adds a `check_figures_equal` test and regenerates 16 baseline files.

### Findings

**1. Regression: operators used as the body of `\overset`/`\underset` lose their spacing, and a regenerated baseline hides it.**
`lib/matplotlib/_mathtext.py:2477`
The body is parsed from `{...}`, so for `\overset{f}{\rightarrow}` the arrow sees `prev_char == '{'` and `next_char == '}'` and gets no space on either side. That is exactly `lightweight_math_tests[1]` (`x \overset{f}{\rightarrow} … \underset{f}{\leftarrow} x`, gh-18241), and `mathtext1_dejavusans_01.png` was regenerated in this branch. The new image is not "more correct": in amsmath, `\overset` keeps a relation as `\mathrel`, so TeX keeps the thick spaces around it.
```python
fig.text(.1, .5, r"$x \overset{f}{\rightarrow} y$")
# main: x  →  y  (arrow spaced)     PR: x→y (cramped)     (not executed)
```
Fix: drop `'{'`/`'}'` from the new boundary sets so that only the true start or end of the math string counts. That still fixes gh-23315 (`a$=b$`) and leaves argument braces alone. Then restore the old `mathtext1_dejavusans_01.png` and add a `check_figures_equal` case for `\overset{f}{\rightarrow}`.

**2. Regression: `\boldsymbol` silently stops bolding (or may crash on) an operator at the start of its argument.**
`lib/matplotlib/_mathtext.py:3074`
`boldsymbol` assumes every spaced-symbol `Hlist` is `[space, char, space]` and takes `c.children[1]` as the `Char`. With this change, `\boldsymbol{=b}` or `\boldsymbol{\rightarrow}` produce `[char, (kern), space]` or `[char, (kern)]`:
- `children[1]` is then a `Kern`, so the glyph isn't bolded.
- If the `Hlist` holds only the char, `children[1]` raises `IndexError`.
```python
fig.text(.1, .5, r"$\boldsymbol{=b}$")   # main: bold "="; PR: regular "=" (or IndexError)   (not executed)
```
Fix: the fix for finding 1 avoids this case. Separately, `boldsymbol` should find the `Char` in `c.children` rather than indexing `[1]`.

**3. The rewritten test 71 makes 15 baseline files churn for no reason.**
`lib/matplotlib/tests/test_mathtext.py:117`
Under the new code, the old string `$\hspace{-0.2}\doteq\hspace{-0.2}$` lays out exactly as it does on `main`: `prev_char` is `'}'` and `next_char` is `'\'`, so both spaces are kept. The old baselines would therefore still pass. `test_spaced_operator_at_boundary` already covers the bare `$\doteq$`/`$\leftharpoonup$` cases.
Fix: revert the `math_tests[71]` edit and drop the 15 regenerated `mathtext_*_71.{png,pdf,svg}` files. Regenerating baselines bloats the repo history for good, and maintainers avoid it unless the output really has to change.

**4. The API change note uses the issue number instead of the PR number.**
`doc/api/next_api_changes/behavior/23315-AM.rst:1`
The file should be named after the PR, i.e. `32331-<initials>.rst`.

**5. Nit: the boundary handling is asymmetric and doesn't fully match TeX, though the note says "Following TeX".**
`lib/matplotlib/_mathtext.py:2479`
- `next_char` is a single character, so multi-character right delimiters (`\}`, `\rangle`, `\rbrace`, `\right)`) never count as a boundary. Meanwhile `\{` on the left does match, through its trailing `{`. As a result `$a=)$` and `$a=\}$` space differently.
- A binary operator at the end (`$a+$`) still gets its left space; TeX turns it into an Ord with no space on either side.

Fix: match the next token against the delimiter sets (e.g. `str.startswith` over `_right_delims`), or soften the TeX claim in the note.

### Verdict
The approach is sound (it answers gh-23315 directly), but it needs to stop treating argument braces as math-list boundaries, and the regenerated baselines should be reverted.
